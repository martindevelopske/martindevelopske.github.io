The case for boring backends

2026-01-09 · 4 min read

title: The case for boring backends date: "2026-01-09" description: Why I'd rather work on a system you've never heard of than the latest shiny thing. readingTime: 4 min read

Every six months a new framework promises to change everything. Most of them don't. The systems that actually keep companies running are usually older than the engineers maintaining them, written in languages no one's excited about, and held together by patterns from a textbook published before the cloud existed.

I love those systems. Here's why.

Boring is a feature

A boring backend is one where you can predict what will happen if you change a line of code. There are no hidden control flows, no surprise async hops, no clever metaprogramming that activates only on Tuesdays. You can read it from top to bottom and follow the data.

That property doesn't come for free. Someone made deliberate choices to keep it that way. Each "we don't need that abstraction yet" call adds up.

Boring scales because it has fewer surprises

The interesting failure modes in distributed systems aren't the ones in the textbook — those are well-understood. The dangerous ones are emergent: two boring components combining in a way that nobody noticed at design time. The more "magic" each component has, the more combinations you have to reason about. Boring components compose into systems you can still hold in your head.

When new is worth it

Sometimes the new thing genuinely fits. Use it. But the bar should be "this solves a real problem the boring version can't" — not "this would be more fun to write." If the answer is the latter, build a side project. Leave the production system alone.

What this looks like in practice

  • Postgres until you can prove you need something else.
  • One language per service. Not three.
  • Boring web framework. Boring ORM, or no ORM. Boring deploys.
  • HTTP and JSON. Reach for gRPC, queues, or streaming only when a measured problem demands it.
  • Sync code first; reach for async when latency or concurrency forces your hand.

Boring isn't lazy. It's the discipline of saying not yet a lot. The reward is a system that two years from now you can still understand in the morning, debug at 3 a.m., and hand off to someone new without a week of folklore.
