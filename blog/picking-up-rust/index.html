Why I'm picking up Rust as a JVM engineer

2026-05-12 · 6 min read

title: Why I'm picking up Rust as a JVM engineer date: "2026-05-12" description: A Java/Spring engineer's notes on why Rust is worth the climb. readingTime: 6 min read

I spend most of my working hours in Java. It's a fine language. The ecosystem is huge, the tooling is mature, and Spring Boot will hand you a production-ready service before lunch. So why am I spending my evenings writing Rust?

The honest reason

Curiosity, mostly. But also: Rust forces you to think about things the JVM happily hides. Lifetimes. Ownership. When memory is freed. Whether a value can be shared across threads. These aren't abstract concerns — they're the same concerns I run into when debugging a flaky production system, just made explicit by the compiler.

Java lets you ignore memory. Rust lets you stop having to guess about it.

What clicked first

The borrow checker is the meme, but for me the first real shift was Result<T, E>. Errors as values, not as side channels. After years of throws sprinkled across signatures or — worse — runtime exceptions bubbling up from places they shouldn't, having every fallible operation declare itself was a relief.

// you can't pretend this might not fail
fn read_config(path: &str) -> Result<Config, ConfigError> {
    let file = std::fs::read_to_string(path)?;
    toml::from_str(&file).map_err(ConfigError::Parse)
}

What I'm building to learn

  • A tiny CLI for managing my dotfiles (because of course).
  • An Axum-based HTTP service that mirrors a small piece of an API I work with daily.
  • A toy Kafka consumer in Rust to compare against the JVM one I wrote at work.

What's still hard

Async Rust. The ecosystem is healthy but the mental model — futures, executors, Pin, Send bounds — takes work. Coming from Java's CompletableFuture, it's both more powerful and less forgiving.

I'll write more as I go. If you're on the same journey from JVM-land, drop me an email — I'd love to compare notes.
